# ProGen2 推理优化方案

> 先导杯 · 面向国产DCU的ProGen2蛋白质序列生成推理优化

---

## 一、模型架构与基线瓶颈分析

### 1.1 ProGen2-medium 架构参数

| 参数 | 值 |
|---|---|
| 层数 n_layer | 27 |
| 隐藏维度 n_embd | 1536 |
| 注意力头数 n_head | 16 |
| 每头维度 head_dim | 96 (1536/16) |
| RoPE 旋转维度 rotary_dim | 48 (每头) |
| 词表大小 vocab_size | **32**（极小） |
| 最大序列长度 | 1024 |
| 中间层 MLP | 6144 (4×1536) |
| 激活函数 | GELU-New |
| 权重总量 | ~3GB (FP32) |

### 1.2 基线实现现状

基线 (`baseline/solution.py`) 做对了的：
- ✅ 使用 `torch.inference_mode()` 禁用梯度
- ✅ 动态 KV Cache（`past_key_values`）
- ✅ 关闭 dropout、关闭 output_attentions / output_hidden_states

基线存在的性能瓶颈：
- ❌ **FP32 全精度**：模型权重、所有中间张量都用 FP32
- ❌ **动态 KV Cache 用 tuple + torch.cat**：每步解码都重新分配内存并拷贝
- ❌ **RoPE 每次 forward 重新计算**：`fixed_pos_embedding()` 每步都算一遍 sin/cos
- ❌ **Causal Mask 用布尔索引 + torch.where**：在 `_attn()` 中做 FP32 mask
- ❌ **lm_head 投影完整 vocab (32)**：虽然 vocab 小，但基线还是先投影再 index_select
- ❌ **没有 torch.compile / 图捕获**：Eager 模式执行
- ❌ **没有算子融合**：GELU、LayerNorm、Attention 都是独立 kernel
- ❌ **Attention 内部强制 FP32**：`query = query.to(torch.float32)` 即使外部是 FP32 也有开销

### 1.3 四项任务特征

| 任务 | Batch | Prefill 长度 | Decode 步数 | 瓶颈阶段 |
|---|---|---|---|---|
| 1 单条生成 | 1 | 32 | 256 | **Decode** |
| 2 多条生成 | 8 | 32 | 256 | **Decode + Batch** |
| 3 生成较长 | 4 | 32 | 512 | **Decode（长）** |
| 4 输入较长 | 4 | 512 | 64 | **Prefill（长）** |

**关键洞察**：任务 1/2/3 的瓶颈是 Decode，任务 4 的瓶颈是 Prefill。优化需要兼顾两者。

## 二、优化方向总览

按 **收益/风险/实现难度** 三维评估，推荐以下优化路线（由易到难）：

```
阶段 1（立即可做，低风险高收益）
├── FP16/BF16 混合精度          → 预期加速 1.5-2x，一致率风险低
├── KV Cache 预分配固定 Buffer    → 预期加速 1.2-1.3x，零风险
├── RoPE sin/cos 预计算          → 预期加速 1.1x，零风险
└── Attention 内部 FP32 强制移除   → 微幅提升，零风险

阶段 2（中等难度，进一步提速）
├── torch.compile 图捕获         → 预期加速 1.2-1.5x，需调参
├── 自定义 Causal Mask 简化       → 预期加速 1.1x，零风险
├── lm_head 仅投影 20 个氨基酸    → 预期加速 1.1x，零风险
└── Prefill / Decode 分离路径     → 预期加速 1.1-1.2x

阶段 3（深度优化，DCU 特有）
├── 自定义 HIP 算子融合          → 预期加速 1.3-2x，需写 HIP
├── INT8 量化推理                → 预期加速 2-3x，一致率有风险
└── Speculative Decoding        → 预期加速 1.5-2x，实现复杂
```

## 三、具体优化方案

### 3.1 精度优化：FP16/BF16 混合精度

**原理**：将模型权重和大部分中间张量从 FP32 降到 FP16/BF16，计算量减半、显存减半。

**DCU 注意事项**：国产 DCU 通常优先支持 BF16（和 AMD MI 系列同源），FP16 可能需要额外确认。建议先试 BF16。

**实现方法**：

```python
# __init__ 中加载模型时指定 dtype
self.model = ProGenForCausalLM.from_pretrained(
    str(self.model_dir),
    torch_dtype=torch.bfloat16,   # 或 torch.float16
    low_cpu_mem_usage=True,
    local_files_only=True,
)
self.model.eval().to(self.device)

# lm_head 输出 logits 仍需 FP32（基线已经这样做了，line 652）
lm_logits = self.lm_head(hidden_states).to(torch.float32)
```

**风险控制**：
- 观察 `consistency_rate`，BF16 通常能保持 99%+ 一致率
- Attention 内部的 FP32 强制转换（基线 line 123-124）要保留或改为条件判断
- lm_head 输出必须转回 FP32 再做 argmax

**预期收益**：
- 模型加载速度提升 2x
- 显存占用从 ~3GB 降到 ~1.5GB
- 计算吞吐提升 1.5-2x（取决于 DCU 的 BF16 算力）

---

### 3.2 KV Cache 预分配固定 Buffer

**问题根源**：基线每步 `torch.cat((past_key, key), dim=-2)` 都重新分配内存并拷贝整个历史 KV。27层 × 256步 = 6912 次 cat。

**优化方案**：在 `__init__` 中一次性预分配最大需要的 KV Cache，后续通过 index_fill 直接写入。

```python
# __init__ 中
max_seq_len = 1024  # config.n_positions
n_layer = 27
n_head = 16
head_dim = 96

# 预分配 [n_layer, 2, B_max, n_head, max_seq_len, head_dim]
# 注意：B_max 要覆盖所有任务的最大 batch（任务2的8）
self.kv_cache_k = torch.zeros(n_layer, 8, n_head, max_seq_len, head_dim,
                              dtype=torch.bfloat16, device=self.device)
self.kv_cache_v = torch.zeros(n_layer, 8, n_head, max_seq_len, head_dim,
                              dtype=torch.bfloat16, device=self.device)

# reset() 中清除
def reset(self):
    self.kv_cache_k.zero_()
    self.kv_cache_v.zero_()

# 每次 generate 中，用 kv_len 追踪当前有效长度
# 写入新 KV：kv_cache_k[layer_idx, :B, :, kv_len:kv_len+new_len, :] = new_k
# Attention 时只看有效范围：kv_cache_k[layer_idx, :B, :, :kv_len+new_len, :]
```

**收益**：
- 消除 6912 次 torch.cat 的内存分配 + 拷贝开销
- 连续内存布局有利于缓存命中
- 预期加速 1.2-1.3x

---

### 3.3 RoPE sin/cos 预计算

**问题根源**：基线 `modeling_progen.py` 中 `fixed_pos_embedding()` 每步 forward 都重新生成 sin/cos。27层 × 256步 = 6912 次。

**优化方案**：在 `__init__` 中预计算最大序列长度的 sin/cos，注册为 buffer。

```python
# __init__ 中
max_seq_len = 1024
rotary_dim = 48

inv_freq = 1.0 / (10000 ** (torch.arange(0, rotary_dim, 2) / rotary_dim))
pos_idx = torch.arange(max_seq_len)
sinusoid_inp = torch.einsum("i , j -> i j", pos_idx, inv_freq).float()
rope_sin = torch.sin(sinusoid_inp).to(self.device)  # [1024, 24]
rope_cos = torch.cos(sinusoid_inp).to(self.device)  # [1024, 24]
```

然后在 Attention forward 中用预计算的 `rope_sin[offset:offset+seq_len]` 代替 `fixed_pos_embedding()` 调用。

**收益**：
- 消除重复的 sin/cos 计算
- 零风险，RoPE 是确定性的

---

### 3.4 移除 Attention 内部不必要的 FP32 强制转换

**问题根源**：`modeling_progen.py` line 123-124：
```python
query = query.to(torch.float32)
key = key.to(torch.float32)
```

**优化方案**：
- 如果外部是 FP32：这两行是 no-op，不影响
- 如果外部是 BF16/FP16：保留 FP32 attention 是为了数值稳定，但可以测试是否能安全移除（一致性可能下降但仍在 80% 阈值以上）

**建议**：先保留，等确认其他优化的一致性没问题后再尝试移除。

---

### 3.5 lm_head 仅投影 20 个氨基酸（可选优化）

**原理**：lm_head 是 `nn.Linear(1536, 32)`，输出 vocab_size=32 的 logits。但我们只需要 20 个氨基酸的 logits。

**基线做法**：先投影 32 维，再 `logits.index_select(-1, allowed_ids)` 取 20 维。

**优化方案 A**（直接）：保持基线做法，vocab=32 太小，这步本身不慢。

**优化方案 B**（极致）：构建一个 32→20 的选择矩阵 `select_matrix = eye(32)[allowed_ids]`，然后：
```python
# allowed_ids 是 20 个 token id
# lm_head.weight: [32, 1536]
# allowed_weight = lm_head.weight[allowed_ids]  # [20, 1536]
# 用这个做线性投影，直接输出 20 维
```

**收益**：vocab=32 太小，收益可忽略。仅在做 INT8 量化时作为配套优化。

---

### 3.6 torch.compile 图捕获

**原理**：用 `torch.compile(model, mode="reduce-overhead")` 让 PyTorch 编译整个 forward graph，减少 Python 调度开销、融合算子。

**实现方法**：

```python
# __init__ 中（模型加载后）
if hasattr(torch, 'compile'):
    self.model = torch.compile(self.model, mode="reduce-overhead")
```

**DCU 注意事项**：
- 国产 DCU 的 PyTorch fork 可能不支持 torch.compile，需先检查 `torch.__version__` 和 DCU 对应版本
- 如果不支持，跳过此步
- 不支持时退而求其次用 `torch.jit.trace` 或 `torch.jit.script`（但 LLM 动态控制流复杂，script 难用）

**收益**：
- 编译后首次运行慢（trace + compile），但后续每次运行快
- 预期 1.2-1.5x 加速
- 图捕获后 Python overhead 几乎消失

---

### 3.7 Prefill / Decode 分离路径

**原理**：
- Prefill：输入长度 L（32 或 512），一次性并行处理，然后把 KV 写入 Cache
- Decode：每次只输入 1 个 token，但要访问全部历史 KV

基线两者共用同一个 `model.forward()`，Decode 时 `next_input = next_token`（shape `[B, 1]`），效率不高。

**优化方案**：

```python
def generate(self, prefixes, max_new_tokens):
    # 1. Prefill：一次性处理全部输入前缀
    input_ids = tokenize(prefixes)  # [B, L]
    
    # 首次 forward，得到初始 KV Cache 写入
    outputs = self.model(input_ids=input_ids, use_cache=True)
    # 把 outputs.past_key_values 拷贝/转存到我们的预分配 Cache 中
    
    # 2. Decode：循环 max_new_tokens 次
    next_token = greedy_select(outputs.logits)  # [B, 1]
    for step in range(max_new_tokens):
        # 只输入当前 token
        outputs = self.model(
            input_ids=next_token,
            use_cache=True,
            # 用预分配的 Cache（或让模型自己管）
        )
        next_token = greedy_select(outputs.logits)  # [B, 1]
        # 收集结果
    
    return decode(generated_tokens)
```

**收益**：
- 逻辑清晰，方便后续对 Prefill 路径做 torch.compile
- 任务 4（长 Prefill）收益较大
- 配合 KV Cache 预分配使用

### 3.8 自定义 HIP 算子融合（进阶）

如果前面优化做完仍有空间，可以考虑写自定义 HIP kernel。**这是难度最高、收益也最大的方向**。

#### 3.8.1 融合 Attention Kernel

将 QKV 投影 + RoPE + Attention + Out Proj 融合成一个 kernel：

```python
# ops/fused_attention.hip
# 输入: hidden_states, kv_cache_k, kv_cache_v, rotary_sin, rotary_cos
# 输出: attn_output, new_k, new_v
# 中间: 不写回 global memory
```

DCU 的 HIP kernel 写法接近 CUDA，可以参考 flash-attn 的实现。

#### 3.8.2 融合 GEMM + Bias + GELU

MLP 层的 fc_in + fc_out 都是 GEMM + GELU / GEMM + 无 bias，可以融合。

#### 3.8.3 融合 lm_head + Greedy Select

lm_head 输出 32 维 logits → 取 20 个氨基酸 → argmax。可以融合成一个 kernel：

```hip
// 直接读 lm_head.weight 的 20 行
// GEMM + 只算 allowed_ids 的 logits + argmax
// 输出 greedy token index
```

**收益**：
- 消除 kernel launch 开销
- 消除中间张量 global memory 读写
- 预期 1.3-2x 端到端加速

---

### 3.9 INT8 量化推理（进阶，需校准）

**原理**：将模型权重量化为 INT8，显存减到 1/4，计算更快。

**允许吗？**：根据 SUBMISSION.md，量化是允许的，但不能"重新训练或微调"。可以用后训练量化（PTQ）。

**实现路径**：

1. **构建校准数据集**：不能用参考答案（违规），但可以：
   - 用 prefill 阶段的 hidden states 做校准
   - 或用随机生成的蛋白质序列做校准

2. **权重 + 激活量化**：
   - 权重：per-channel INT8（对称）
   - 激活：per-tensor INT8（对称，量化范围 [-128, 127]）
   - Attention 内部 accumulator：保留 FP32

3. **实现 INT8 GEMM**：DCU 的 BLAS 库（rocBLAS 或 DCU 对应库）通常支持 INT8 GEMM

**风险**：
- 一致率可能降到 95% 甚至 90% 以下（任务 4 长输入风险更大）
- 必须保证一致率 ≥ 80% 才能拿性能分

**建议**：在阶段 1/2 做完、有了基线加速比后再尝试。如果一致率不达标，放弃这个方向。

---

### 3.10 Speculative Decoding（研究方向）

**原理**：用小模型（draft model）快速猜几个 token，大模型（target model）一次验证并接受/拒绝。

**允许吗？**：根据 SUBMISSION.md，"训练额外推测解码模型，或引入其他模型权重作为草稿模型" **不允许**。

**结论**：放弃这个方向，属于规则禁止的范围。

## 六、评分策略

### 6.1 一致率门槛

四项任务必须 **一致率 ≥ 80%** 才能拿性能分。所有 90%+ 一致率方案都安全，优先保证。

### 6.2 性能分公式

```
单项性能分 = 10 × (所有合格队伍中该项最短耗时) ÷ (本队该项耗时)
```

- 每项满分 10 分，四项共 40 分
- 对照时间来自 **同硬件规格** 的合格队伍

### 6.3 策略建议

1. **先保证一致率 100%**：做阶段 1 的精度无关优化（KV Cache、RoPE 预计算、路径分离）
2. **再引入精度降低**：BF16 通常能保持 99%+ 一致率，安全
3. **最后冒险**：INT8 量化只有在时间充裕且一致率达标时才做

### 6.4 关键数据点

任务 4（输入较长，Prefill=512, Decode=64）的 Prefill 阶段对精度更敏感，量化时重点关注。
