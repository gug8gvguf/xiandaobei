# 参赛作品与优化报告提交要求

## 1. 提交材料与目录结构

每支队伍仅提交1个ZIP文件，包含按统一接口运行的优化源码、一份优化报告及实验依据。运行方法写在报告中，不另交学生README。压缩包名采用 `progen2_` 加队长真实学号的形式，例如 `progen2_2025001234.zip`，其中数字须替换为队长真实学号，不使用中文或空格。报告正文中的中文姓名和队名正常填写。

将 `submission/` 文件夹压缩为ZIP。包内只能有一个顶层 `submission/` 目录，不得修改目录名，也不得在其外层再包含 `progen2_contest/`。目录结构如下：

```text
submission/
├── solution.py              必须，Solution统一入口
├── ...                      必须，全部新增或修改的源码
├── report.pdf               必须，可替换为report.docx，二选一
├── evidence/                必须，测试原始结果与完整日志
│   ├── baseline_public.json 基准结果；自定义文件名须在报告中说明
│   ├── submission_public.json 本队结果；自定义文件名须在报告中说明
│   ├── baseline.log         必须，FP32基准测试完整日志
│   ├── submission.log       必须，最终优化程序测试完整日志
│   └── ...                  报告引用的其他实验依据（如有）
├── build.sh                 可选，离线构建一次
├── src/                     可选，自有Python/C++源码
├── ops/                     可选，自定义HIP算子源码
├── models/                  可选，修改后的模型计算源码
└── calibration/             可选，量化需要的可复现校准资产
```

`src/`、`ops/`、`models/`、`build.sh` 和 `calibration/` 仅在实际使用时提交；目录示例中的 `...` 表示本队实际文件，不是要求创建的文件名。上述英文数字命名要求针对压缩包文件名；顶层目录保持 `submission/`，报告采用 `report.pdf` 或 `report.docx`，不要求重命名全部源码文件。

## 2. 提交材料要求

- 完整的 `solution.py`、所有新增或修改的源码及自有依赖源码，遵守 [统一接口](INTERFACE.md)。
- 按 [报告模板](报告模板.docx) 撰写一份优化报告，固定命名为 `report.pdf` 或 `report.docx`（二选一），填写参赛信息、实验环境、运行说明、优化实现、实验结果和成员分工。
- 如使用自定义扩展，提交相应源码和必要构建脚本，不能只交个人容器内已有的二进制文件。
- 将题目包 `results/baseline_public.json`、`results/submission_public.json`、`results/baseline.log` 和 `results/submission.log` 这4个文件复制到 `submission/evidence/`。两个完整日志均为必交材料，应保留命令从开始到结束的终端输出，包括环境信息、四项任务结果及警告或报错，不能只交截图、摘录或手工汇总。作品记录和日志须来自最终提交代码对应的一轮完整测试，并同时提供同规格FP32基准记录和日志；不要求提交全部调试历史，不得按负载拼接不同轮次或不同代码版本的最好结果。已有自定义结果或日志文件名时，在报告中说明对应关系，无需仅为统一文件名重新测试。正常完成的测试须提交原始JSON；如测试因报错未生成某份JSON，提交对应完整报错日志，并在报告中说明缺失原因，不得伪造结果文件，也不得使用旧JSON替代本轮记录。
- 如采用量化，提交从公共权重可复现转换的代码和必要校准资产；校准数据可直接提供，或提供可离线运行的确定性生成脚本、种子及来源说明。

按 [基准运行说明](BASELINE.md) 中带 `tee` 的命令完成测试后，从题目包根目录执行以下命令，将结果与日志放入提交目录：

```bash
mkdir -p submission/evidence
cp results/baseline_public.json results/submission_public.json results/baseline.log results/submission.log submission/evidence/
```

上述复制命令适用于测试正常完成、4个文件均已生成的情况。测试失败时按前述异常说明提交本轮完整日志，不要补造缺失的JSON。

公共 `pytorch_model.bin`（约3 GB）和统一Tokenizer由题目包提供，不得重复打包，也不能换用其他版本。不打包整个题目包、`baseline/`、测试工具、固定测试数据、环境目录、`.cache/`、`__pycache__/`、`*.pyc`、无关临时文件或个人数据；不需要提交或编写评分工具。

## 4. 报告评分

报告共10分，按以下三部分审阅报告及实验依据。可以如实记录失败实验，程序失败不自动取消报告分；说明和结果应与提交代码及日志一致。

| 类别 | 分值 | 说明 |
|---|---:|---|
| 运行说明 | 3 | 环境配置、代码组织及运行步骤 |
| 优化说明 | 4 | 性能瓶颈、代码修改、实现方法与优化原理 |
| 实验与总结 | 3 | 四负载性能和一致性结果、结果分析、成员分工及来源 |

完整总分为基础运行25分＋一致性25分＋推理性能40分＋报告10分。四项测试任务各占10分性能分，独立判断：该项完整运行、输出格式合格且一致率达到80%，才按 `10×该项所有合格队伍中的最短耗时÷本队该项耗时` 计分。对照时间来自相同硬件规格和加速卡数量下的合格队伍，不以FP32基准耗时代替。

正常完成以JSON原始数值为准；异常时仅有可核验日志的，按日志记录值核算。

## 5. 允许修改和不能修改的边界

### 允许

- 在保持统一模型任务和生成规则的前提下，调整推理计算精度、数据布局和内部等价计算实现。
- 优化缓存与显存管理、执行流程及DCU上的程序实现。
- 增加满足统一接口和资源要求的Python、C++或HIP源码，以及必要构建脚本。

### 不允许

- 更换ProGen2-medium、使用其他预训练权重、修改统一Tokenizer或改变确定性生成规则。
- 剪枝、删层、删除注意力头、改变层数或隐藏维度，以及替换为重新设计的网络。
- 重新训练或微调主模型；训练额外推测解码模型，或引入其他模型权重作为草稿模型。
- 使用参考答案进行训练、拟合或量化校准，或以量化名义重新训练。
- 硬编码、预存或查表返回参考答案，跳过真实推理，改变B/L/G、少生成或提前停止。
- 跨请求复用生成结果或输入相关KV，干扰同步/计时，或为正确性和速度使用不同程序行为。
- 使用未分配设备、远程服务、CPU多线程或多进程优化；把规定DCU推理转移到其他设备。
- 修改测试程序或参考输出，联网下载、计时生成时安装依赖/编译/训练，以及伪造结果或日志。

本题固定同一预训练模型，比较DCU上的推理执行效率。剪枝、架构改变或额外训练会引入模型能力、训练数据和训练资源差异，因此不属于本题开放范围；内部计算实现、精度、缓存、流程与算子仍可充分优化。

## 6. 提交前检查

核对作品测试记录，确认四种负载的返回数量、长度、顺序、字符和实际一致率。仅有 `baseline/` 结果不能证明本队程序可用；已有与提交版本对应的有效结果时，不要求为打包重新测试。

确认正常完成测试的原始JSON及完整日志已复制到 `submission/evidence/`；如某份JSON因测试报错未生成，已提交对应完整报错日志并在报告中说明缺失原因，未伪造结果文件。测试器遇异常会退出：日志中已完成且可核验的负载仍可计分，失败、未执行或无有效记录的负载一致率和性能分为0，基础运行分为0；其他有效负载与报告独立计分。确认报告已按固定名称保存，全部新增或修改的源码及实际使用的构建、校准资料已纳入 `submission/`。确认报告中的运行命令与交付文件一一对应，模型和Tokenizer路径由调用参数传入，不依赖个人账号或绝对目录。

将 `submission/` 文件夹压缩为1个ZIP，按队长真实学号命名，并检查压缩包仅有顶层 `submission/`，未包含公共权重、Tokenizer、测试工具、环境或缓存目录。
